# Discovery และ Information Architecture

อ่านเมื่อวางหน้าใหม่ เปลี่ยนลำดับข้อมูล หรือรีวิวว่าหน้าจอช่วยงานผู้ใช้จริงหรือไม่

## กำหนด Design Brief ตามขนาดงาน

เก็บข้อมูลต่อไปนี้จาก source, หน้าจอเดิม และ requirement ก่อนถามสิ่งที่ค้นได้เอง:

- Audience: ใครใช้ มีสิทธิ์เห็นข้อมูลระดับใด ใช้บ่อยเพียงใด
- Decision: หลังเปิดหน้านี้ต้องตอบคำถามหรือตัดสินใจอะไร
- Next action: ดูรายละเอียด จัดการรายการ อนุมัติ เปรียบเทียบ หรือดาวน์โหลด
- Context: desktop/mobile, จอประชุม, การใช้งานภาคสนาม, ภาษา และข้อจำกัดเครือข่าย
- Data: แหล่งข้อมูล ความถี่อัปเดต ความครบถ้วน และข้อจำกัดที่ทราบ
- Constraints: design system, routes, API, scope ของงาน และสิ่งที่ห้ามเปลี่ยน

สรุปเป็น brief สั้นสำหรับงานเล็ก ไม่บังคับสร้างเอกสารใหม่ทุกครั้ง ถ้าขาดข้อมูลที่เปลี่ยนทิศทางการออกแบบอย่างมีนัยสำคัญให้ถามผู้ใช้

## เลือกโครงสร้างตามงาน ไม่ใช่ตามเทมเพลต

| ลักษณะหน้า | สิ่งที่ควรเด่น | สิ่งที่ไม่ควรกลบงานหลัก |
|---|---|---|
| Operational dashboard | งานค้าง/ข้อยกเว้นและ action ที่ทำต่อได้ | กราฟภาพรวมจำนวนมากที่ไม่ช่วยจัดลำดับงาน |
| Executive dashboard | ผลลัพธ์ แนวโน้ม เป้าหมาย และข้อจำกัดของข้อมูล | รายละเอียดรายบุคคลและปุ่มที่ไม่มีสิทธิ์ใช้งาน |
| Analytical report | ขอบเขตข้อมูล ตัวกรอง การเปรียบเทียบและรายละเอียด | KPI ที่เปลี่ยนตาม filter โดยไม่บอกความหมาย |
| List/work queue | ค้นหา filter สถานะ และการจัดการรายการ | Hero/header ขนาดใหญ่ที่ดันรายการพ้นจอ |
| Form/detail | ข้อมูลจำเป็น ลำดับขั้น ข้อผิดพลาด และการบันทึก | Dashboard cards ที่แทรกใน workflow โดยไม่จำเป็น |

หน้าเดียวอาจมีหลายหน้าที่ได้ แต่ต้องระบุหน้าที่หลักและแยก section ให้เข้าใจ หลีกเลี่ยงการทำหน้าสำหรับทุก role ให้เหมือนกันโดยไม่ดูงานจริง

## วางลำดับการอ่าน

เริ่มจาก page identity และขอบเขต → ข้อมูล/งานสำคัญ → หลักฐานสนับสนุน → รายละเอียด โดยปรับตาม task ไม่ใช้เป็น layout บังคับ
วาง filter ใกล้สิ่งที่มันควบคุม หาก filter ใช้ทั้งหน้าให้แสดง scope ชัด หากใช้เฉพาะกราฟอย่าวางให้ดูเหมือน global
กลุ่มข้อมูลเดียวกันควรอยู่ใกล้กัน ชื่อ section ต้องสื่อความหมายธุรกิจ ไม่ตั้งชื่อเพียง “ข้อมูล 1/2”
กำหนด primary action ตาม context; action ที่มีผลร้ายแรงไม่ควรดูเด่นเท่าปุ่มทำงานปกติโดยไม่มีเหตุผล
รักษา reading order ใน DOM ให้สอดคล้องภาพ โดยเฉพาะเมื่อ desktop มีหลายคอลัมน์

## ก่อนลงรายละเอียดภาพ

ทำ wireframe แบบข้อความหรือโครงสร้าง component เท่าที่ช่วยตัดสินใจ ไม่ต้องสร้างภาพทุกงาน
เช็กว่าทุก block ตอบคำถามอะไร ใช้ข้อมูลจากไหน และผู้ใช้ทำอะไรต่อได้ ถ้าตอบไม่ได้ให้ตัดออกหรือระบุเป็นข้อเสนอที่ยังไม่ยืนยัน
เมื่อเปลี่ยนหน้าเดิม ให้ map ส่วนเก่า→ส่วนใหม่เพื่อไม่ทำ filter, export, action หรือคำเตือนหาย
การซ่อนตาม role ต้องอิง capability จริง; การไม่เห็นปุ่มไม่ได้ทดแทน server authorization

## ตรวจรับโครงสร้าง

- ผู้ใช้แยกได้ว่ากำลังดูข้อมูลของใคร ช่วงใด และมีข้อจำกัดอะไร
- งานสำคัญค้นเจอได้โดยไม่ต้องตีความกราฟหลายชุดก่อน
- ไม่ใช้หลายชื่อกับ metric เดียว หรือชื่อเดียวกับ metric คนละนิยาม
- รายละเอียดและ action สำคัญยังเข้าถึงได้ใน viewport เล็กและ role ที่เกี่ยวข้อง
