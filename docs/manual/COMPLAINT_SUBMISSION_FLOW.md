# Flow การส่งและดำเนินการเรื่องร้องเรียน

เอกสารนี้อธิบายลำดับการส่งและดำเนินการเรื่องร้องเรียนของระบบ Damrongdham SSK ตั้งแต่รับเรื่องเข้าสู่ระบบ คัดกรอง ส่งต่อหน่วยงาน ติดตามผล จนถึงการปิดเรื่อง โดยอ้างอิงจาก Implementation ปัจจุบัน

> อัปเดตล่าสุด: 13 กันยายน 2569

## 1. ภาพรวม Flow

```text
ประชาชนหรือเจ้าหน้าที่ยื่นเรื่อง
              │
              ▼
          NEW — เรื่องใหม่
              │ ศูนย์เริ่มคัดกรอง
              ▼
        SCREENING — กำลังคัดกรอง
              │
              ├── ปฏิเสธ ───────────────────────────────► REJECTED
              │
              ├── ศูนย์ดำรงธรรมจัดการเอง
              │          ▼
              │     IN_PROGRESS ── ศูนย์ปิดเรื่อง ─────► CLOSED
              │
              └── ส่งต่อหน่วยงาน
                         ▼
                     ASSIGNED
                         │
                         ├── หน่วยงานส่งคืน ────────────► RETURNED
                         │                                  │
                         │                       ศูนย์คัดกรองใหม่
                         │                                  ▼
                         │                              SCREENING
                         │
                         └── หน่วยงานรับเรื่อง
                                    ▼
                                ACCEPTED
                                    │
                                    ├── ส่งคืน ──────────► RETURNED
                                    │
                                    └── เริ่มดำเนินการ
                                               ▼
                                          IN_PROGRESS
                                               │ ส่งผลดำเนินการ
                                               ▼
                                            RESOLVED
                                               │ ศูนย์เริ่มตรวจผล
                                               ▼
                                           REVIEWING
                                               │
                                               ├── ผลผ่าน ─► CLOSED
                                               │
                                               └── ส่งกลับแก้ไข
                                                        ▼
                                                   IN_PROGRESS
```

สถานะ `CLOSED` และ `REJECTED` เป็นสถานะสิ้นสุด ปัจจุบันระบบไม่รองรับการเปิดเรื่องกลับมาดำเนินการใหม่

## 2. ผู้เกี่ยวข้องใน Flow

| กลุ่มผู้ใช้ | Role | หน้าที่หลักใน Workflow |
|---|---|---|
| ประชาชนทั่วไป | Guest/Public | ยื่นเรื่องโดยไม่ Login และติดตามด้วยเลขที่เรื่อง |
| สมาชิกประชาชน | Citizen | ยื่นเรื่อง ดูรายการเรื่องของตน และติดตามสถานะ |
| เจ้าหน้าที่ศูนย์ดำรงธรรม | `officer`, `chief` | รับเรื่อง คัดกรอง ส่งต่อ ตรวจผล ส่งกลับแก้ไข และปิดเรื่อง |
| ผู้ดูแลระบบ | `super_admin`, `admin` | ทำ Workflow ฝั่งศูนย์ได้ตาม Implementation ปัจจุบัน |
| เจ้าหน้าที่หน่วยงานปลายทาง | `agency_officer`, `agency_head` | รับหรือส่งคืนเรื่อง เริ่มดำเนินการ อัปเดตความคืบหน้า และส่งผลกลับ |
| ผู้บริหาร | `executive` | ดู Dashboard และรายงาน ไม่มีสิทธิ์เปลี่ยนสถานะเรื่อง |
| ระบบอัตโนมัติ | Scheduled Jobs | ตรวจใกล้ครบกำหนด เกิน SLA และเรื่องที่ไม่มีการอัปเดต |

## 3. ช่องทางนำเรื่องเข้าสู่ระบบ

เรื่องร้องเรียนเข้าสู่ระบบได้ 3 ช่องทางหลัก

### 3.1 ประชาชนทั่วไปแบบ Guest

- ยื่นผ่านหน้าสาธารณะโดยไม่ต้อง Login
- กรอกข้อมูลผู้ร้อง รายละเอียดเรื่อง ประเภทเรื่อง พื้นที่เกิดเหตุ และข้อมูลที่เกี่ยวข้อง
- เลือกปกปิดตัวตนและแนบไฟล์หลักฐานได้
- เมื่อบันทึกสำเร็จ ระบบออกเลขที่เรื่องรูปแบบ `DC-YYYYMM-XXXX`
- เรื่องเริ่มต้นที่สถานะ `NEW`
- ประชาชนต้องเก็บเลขที่เรื่องไว้ใช้ติดตามผ่านหน้า Public Tracking

### 3.2 สมาชิกประชาชน

- Login แล้วส่งเรื่องผ่านระบบสมาชิก
- เรื่องถูกผูกกับบัญชี Citizen
- ดูรายการและรายละเอียดเรื่องของตนได้โดยไม่ต้องจำเลขที่เรื่อง
- เลือกปกปิดตัวตนและแนบไฟล์หลักฐานได้
- เรื่องเริ่มต้นที่สถานะ `NEW` เช่นเดียวกับ Guest

### 3.3 เจ้าหน้าที่บันทึกเรื่องแทนประชาชน

- เจ้าหน้าที่ศูนย์ดำรงธรรมบันทึกเรื่องที่รับมาจากช่องทางอื่น เช่น Walk In โทรศัพท์ จดหมาย หรือหน่วยงานอื่น
- ระบบบันทึกผู้รับเรื่องและออกเลขที่เรื่อง
- เรื่องเริ่มต้นที่สถานะ `NEW` และใช้ Workflow เดียวกับเรื่องที่ประชาชนยื่นเอง

การเป็นเรื่องปกปิดตัวตน (`is_anonymous`) ไม่เปลี่ยนลำดับ Workflow ระบบเพียงปกปิดข้อมูลส่วนบุคคลจากผู้ใช้งานตามสิทธิ์

## 4. ขั้นตอนดำเนินการโดยละเอียด

### ขั้นตอนที่ 1: รับเรื่องใหม่

| หัวข้อ | รายละเอียด |
|---|---|
| สถานะ | `NEW` — ใหม่ |
| ผู้ดำเนินการต่อ | เจ้าหน้าที่หรือหัวหน้าศูนย์ดำรงธรรม |
| การดำเนินการ | ตรวจข้อมูลเบื้องต้น แล้วกด “เริ่มคัดกรอง” |
| สถานะถัดไป | `SCREENING` |

### ขั้นตอนที่ 2: คัดกรองเรื่อง

เมื่อเรื่องอยู่ในสถานะ `SCREENING` ศูนย์ดำรงธรรมตรวจความครบถ้วน จัดประเภทเรื่อง กำหนดพื้นที่ ความสำคัญ และพิจารณาหน่วยงานที่รับผิดชอบ โดยเลือกได้ 3 ทาง

#### ทางเลือก A: ส่งต่อหน่วยงานปลายทาง

- เลือกหน่วยงานที่เกี่ยวข้องและระบุหมายเหตุได้
- ระบบสร้างรายการมอบหมายที่มีสถานะ `PENDING`
- ระบบเปลี่ยนสถานะเรื่องเป็น `ASSIGNED`
- ระบบคำนวณ `due_date` จากวันที่ส่งต่อและจำนวนวัน SLA ของประเภทเรื่อง
- ระบบยกเลิก Assignment เดิมที่ยัง Active ก่อนสร้าง Assignment ใหม่
- หน่วยงานปลายทางได้รับการแจ้งเตือนตามช่องทางที่ตั้งค่าไว้

```text
due_date = วันที่ส่งต่อ + จำนวนวัน SLA ของประเภทเรื่อง
```

หากเรื่องไม่มี Category หรือไม่พบค่า SLA ระบบใช้ค่าเริ่มต้น 15 วัน

#### ทางเลือก B: ศูนย์ดำรงธรรมจัดการเอง

- ใช้เมื่อเรื่องไม่จำเป็นต้องส่งไปยังหน่วยงานภายนอก
- ระบบสร้าง Assignment ให้หน่วยงานที่ตั้งค่า `is_center = 1`
- Assignment ของศูนย์มีสถานะ `ACCEPTED` ทันที
- ระบบคำนวณ `due_date` เช่นเดียวกับการส่งต่อหน่วยงาน
- สถานะเรื่องเปลี่ยนจาก `SCREENING` เป็น `IN_PROGRESS`
- เมื่อดำเนินการเสร็จ ศูนย์กรอกสรุปผลและปิดเรื่องเป็น `CLOSED` ได้โดยตรง

#### ทางเลือก C: ปฏิเสธเรื่อง

- ใช้ในกรณีเรื่องซ้ำ ข้อมูลไม่เพียงพอ ไม่อยู่ในอำนาจหน้าที่ หรือไม่ผ่านหลักเกณฑ์
- ต้องระบุเหตุผลการปฏิเสธ
- สถานะเปลี่ยนจาก `SCREENING` เป็น `REJECTED`
- `REJECTED` เป็นสถานะสิ้นสุด

### ขั้นตอนที่ 3: หน่วยงานพิจารณารับเรื่อง

เมื่อเรื่องอยู่ในสถานะ `ASSIGNED` เจ้าหน้าที่หรือหัวหน้าของหน่วยงานที่ได้รับมอบหมายเท่านั้นที่ดำเนินการได้

#### รับเรื่อง

- หน่วยงานกด “รับเรื่อง”
- Assignment เปลี่ยนจาก `PENDING` เป็น `ACCEPTED`
- สถานะเรื่องเปลี่ยนจาก `ASSIGNED` เป็น `ACCEPTED`
- ศูนย์ดำรงธรรมได้รับการแจ้งว่าหน่วยงานรับเรื่องแล้ว

#### ส่งคืนเรื่อง

- หน่วยงานกด “ส่งคืน” และต้องระบุเหตุผล
- ส่งคืนได้ทั้งก่อนรับเรื่อง (`ASSIGNED`) และหลังรับเรื่อง (`ACCEPTED`)
- สถานะเรื่องเปลี่ยนเป็น `RETURNED`
- ศูนย์ดำรงธรรมเริ่มคัดกรองใหม่ ทำให้เรื่องกลับเป็น `SCREENING`
- หลังคัดกรองใหม่ ศูนย์สามารถส่งต่อหน่วยงานใหม่ จัดการเอง หรือปฏิเสธได้

### ขั้นตอนที่ 4: หน่วยงานเริ่มดำเนินการ

- เมื่อ Assignment และเรื่องอยู่ในสถานะ `ACCEPTED` หน่วยงานกด “เริ่มดำเนินการ”
- สถานะเรื่องเปลี่ยนเป็น `IN_PROGRESS`
- หน่วยงานสามารถบันทึกความคืบหน้า แนบไฟล์ และขอข้อมูลเพิ่มเติมจากผู้ร้องได้ตามสิทธิ์
- การอัปเดตชนิด `PROGRESS` จะรีเซ็ตตัวนับการเร่งรัด และเริ่มนับระยะไม่มีความคืบหน้าใหม่

### ขั้นตอนที่ 5: หน่วยงานส่งผลดำเนินการ

- หน่วยงานกด “ส่งผลดำเนินการ”
- ต้องระบุผลการดำเนินงานในช่อง `content`
- ระบบบันทึก Update ชนิด `RESULT`
- สถานะเรื่องเปลี่ยนจาก `IN_PROGRESS` เป็น `RESOLVED`
- ศูนย์ดำรงธรรมได้รับการแจ้งให้ตรวจสอบผล

### ขั้นตอนที่ 6: ศูนย์ตรวจสอบผล

- ศูนย์กด “เริ่มตรวจผล”
- สถานะเปลี่ยนจาก `RESOLVED` เป็น `REVIEWING`
- ศูนย์ตรวจเนื้อหาผลดำเนินการและหลักฐานที่หน่วยงานส่งมา

ศูนย์เลือกได้ 2 ทาง

#### ผลดำเนินการครบถ้วน

- กด “ปิดเรื่อง”
- ต้องระบุสรุปผลการดำเนินงาน (`closed_summary`)
- ระบบบันทึกวันที่และผู้ปิดเรื่อง
- สถานะเปลี่ยนจาก `REVIEWING` เป็น `CLOSED`

#### ผลดำเนินการยังไม่ครบถ้วน

- กด “ส่งกลับให้หน่วยงานแก้ไข”
- หน้าเว็บกำหนดให้ระบุเหตุผลหรือสิ่งที่ต้องแก้
- สถานะเปลี่ยนจาก `REVIEWING` กลับเป็น `IN_PROGRESS`
- หน่วยงานแก้ไขและกดส่งผลดำเนินการใหม่
- วงรอบจึงกลับไปที่ `RESOLVED → REVIEWING` จนกว่าศูนย์จะยอมรับผลและปิดเรื่อง

| สถานะปัจจุบัน | Action | ผู้ดำเนินการ | สถานะถัดไป | ข้อมูลบังคับ |
|---|---|---|---|---|
| `NEW` | เริ่มคัดกรอง | ศูนย์ | `SCREENING` | — |
| `SCREENING` | ส่งต่อหน่วยงาน | ศูนย์ | `ASSIGNED` | หน่วยงาน |
| `SCREENING` | ศูนย์จัดการเอง | ศูนย์ | `IN_PROGRESS` | — |

| `ASSIGNED` | รับเรื่อง | หน่วยงานที่ได้รับมอบหมาย | `ACCEPTED` | — |

| `ACCEPTED` | เริ่มดำเนินการ | หน่วยงานที่ได้รับมอบหมาย | `IN_PROGRESS` | — |

| `RETURNED` | เริ่มคัดกรองใหม่ | ศูนย์ | `SCREENING` | — |

## 6. SLA และการเร่งรัดระหว่างดำเนินการ

- SLA เริ่มนับเมื่อศูนย์ส่งต่อเรื่อง หรือเลือกให้ศูนย์จัดการเอง
- Phase ปัจจุบันนับรวมวันเสาร์ อาทิตย์ และวันหยุด
- เมื่อวันปัจจุบันเลย `due_date` และเรื่องยังไม่ปิดหรือปฏิเสธ ระบบตั้ง `is_overdue = true`
- เรื่องที่ไม่มีการอัปเดตความคืบหน้าจะถูกเร่งรัดระดับ L1, L2 และ L3 ตามเกณฑ์ 30, 45 และ 52 วัน
- การเกิน SLA และการถูกเร่งรัดเป็นคนละเงื่อนไข เรื่องหนึ่งสามารถเข้าเงื่อนไขอย่างใดอย่างหนึ่งหรือทั้งสองอย่างพร้อมกันได้

รายละเอียดเพิ่มเติมดู [เรื่องที่ถูกเร่งรัด และเรื่องเกินกำหนด SLA](./SLA_AND_ESCALATION.md)

## 7. การแจ้งเตือน

ระบบสร้างการแจ้งเตือนตามเหตุการณ์สำคัญ เช่น

- มีเรื่องร้องเรียนใหม่
- ศูนย์ส่งต่อเรื่องให้หน่วยงาน
- หน่วยงานรับหรือส่งคืนเรื่อง
- หน่วยงานเริ่มดำเนินการและส่งผลกลับ
- ศูนย์เริ่มตรวจผล ส่งกลับแก้ไข หรือปิดเรื่อง
- เรื่องใกล้ครบกำหนด เกิน SLA หรือไม่มีความคืบหน้านานถึงเกณฑ์

ผู้รับการแจ้งเตือนขึ้นอยู่กับเหตุการณ์ หน่วยงานที่รับผิดชอบ และการตั้งค่าช่องทางแจ้งเตือนของระบบ

## 8. สิ่งที่ประชาชนเห็น

ประชาชนเห็นสถานะแบบย่อผ่านหน้า Public Tracking หรือหน้า “เรื่องของฉัน”

| สถานะภายใน | สถานะที่ประชาชนเห็น |
|---|---|
| `NEW`, `SCREENING` | รับเรื่องแล้ว — กำลังตรวจสอบข้อมูล |
| `ASSIGNED`, `ACCEPTED` | ส่งต่อหน่วยงานที่รับผิดชอบแล้ว |
| `IN_PROGRESS` | กำลังดำเนินการ |
| `RESOLVED`, `REVIEWING` | อยู่ระหว่างตรวจสอบผลดำเนินการ |
| `RETURNED` | อยู่ระหว่างประสานงานกับหน่วยงาน |
| `CLOSED` | ดำเนินการเสร็จสิ้น |
| `REJECTED` | ไม่สามารถดำเนินการได้ พร้อมเหตุผลที่เปิดเผย |

ประชาชนไม่เห็นข้อมูลภายในทั้งหมด เช่น หมายเหตุภายใน ข้อมูลผู้ใช้งาน หรือรายละเอียดการประสานงานระหว่างศูนย์กับหน่วยงาน

## 9. การบันทึกประวัติและความปลอดภัยของข้อมูล

- ทุกการเปลี่ยนสถานะถูกบันทึกใน `complaint_status_logs`
- Action สำคัญถูกบันทึกใน Audit Log พร้อมผู้ดำเนินการ เวลา และข้อมูลประกอบ
- ผู้ใช้หน่วยงานปลายทางเห็นเฉพาะเรื่องที่ส่งให้หน่วยงานของตน
- หน่วยงานปลายทางไม่เห็นข้อมูลส่วนบุคคลของผู้ร้อง
- เรื่องปกปิดตัวตนถูก Mask สำหรับ Staff ทุก Role
- เฉพาะ `super_admin` ที่เปิดเผยตัวตนได้ โดยต้องระบุเหตุผลและระบบบันทึกประวัติการเปิดเผย

## 10. ข้อสังเกตจาก Implementation ปัจจุบัน

### 10.1 การสร้างเรื่องผ่าน Staff API

Frontend ตั้งใจให้เจ้าหน้าที่ศูนย์เป็นผู้บันทึกเรื่อง แต่ Backend ปัจจุบันอนุญาต `agency_officer` และ `agency_head` เรียก `POST /api/complaints` ได้ด้วย แม้หน้าเว็บของหน่วยงานจะไม่มีปุ่มสร้างเรื่อง ควรจำกัด Backend ให้ตรงกับเจตนาของ Workflow

### 10.2 เหตุผลการส่งกลับแก้ไข

หน้าเว็บบังคับกรอกเหตุผลเมื่อศูนย์ส่งผลกลับให้หน่วยงานแก้ไข แต่ Controller ปัจจุบันไม่ได้ส่งค่า `note` เข้า Service จึงมีโอกาสที่เหตุผลจะไม่ถูกบันทึกใน Status Log

### 10.3 การปิดเรื่องจากสถานะ IN_PROGRESS

หน้าเว็บแสดงปุ่มปิดเรื่องจาก `IN_PROGRESS` เฉพาะเรื่องที่ศูนย์จัดการเอง แต่ Transition ใน Backend อนุญาต Center Role ปิดเรื่องจาก `IN_PROGRESS` ได้โดยไม่ได้ตรวจว่า Active Assignment เป็นหน่วยงานศูนย์ การเรียก API โดยตรงจึงอาจข้ามขั้นตอนส่งผลและตรวจผลของหน่วยงานปลายทางได้
