# Roles, Permissions และบัญชีทดสอบ

เอกสารนี้สรุปประเภทผู้ใช้งาน สิทธิ์ตาม implementation ปัจจุบัน และบัญชีทดสอบที่สร้างจาก Seed Data ของระบบ Damrongdham SSK

> อัปเดตล่าสุด: 13 กันยายน 2569

## 1. โครงสร้างผู้ใช้งาน

ระบบแบ่งผู้ใช้งานเป็น 4 กลุ่มหลัก

1. **ผู้ดูแลระบบและเจ้าหน้าที่ศูนย์ดำรงธรรม** — `super_admin`, `admin`, `officer`, `chief`
2. **เจ้าหน้าที่หน่วยงานปลายทาง** — `agency_officer`, `agency_head`
3. **ผู้บริหารสำหรับดูข้อมูลภาพรวม** — `executive`
4. **ประชาชนผู้ยื่นและติดตามเรื่อง** — `public` และบัญชีสมาชิก `Citizen`

### ความหมายของ Center และ Agency

- `officer` และ `chief` คือเจ้าหน้าที่ของ **ศูนย์ดำรงธรรม** ซึ่งเป็นหน่วยงานกลางที่รับเรื่อง คัดกรอง ส่งต่อ ตรวจสอบผล และปิดเรื่อง
- `agency_officer` และ `agency_head` คือเจ้าหน้าที่ของ **หน่วยงานอื่นที่ศูนย์ดำรงธรรมส่งเรื่องให้ดำเนินการ** เช่น สำนักงานที่ดิน อำเภอ หรือส่วนราชการที่เกี่ยวข้อง
- ผู้ใช้กลุ่ม Agency จะเห็นเฉพาะเรื่องที่ถูกส่งให้หน่วยงานของตน และไม่เห็นข้อมูลส่วนบุคคลของผู้ร้อง

ลำดับการทำงานหลักเป็นดังนี้

```text
ประชาชนยื่นเรื่อง
      ↓
ศูนย์ดำรงธรรมรับและคัดกรอง (officer/chief)
      ↓
ส่งต่อหน่วยงานที่เกี่ยวข้อง
      ↓
หน่วยงานรับและดำเนินการ (agency_officer/agency_head)
      ↓
ส่งผลกลับให้ศูนย์ดำรงธรรม
      ↓
ศูนย์ตรวจสอบและปิดเรื่อง
```

## 2. Roles และสิทธิ์ที่ทำได้จริง

### `super_admin` — ผู้ดูแลระบบสูงสุด

- จัดการเรื่องร้องเรียนทั้งหมดในฐานะเจ้าหน้าที่ศูนย์
- สร้าง แก้ไข คัดกรอง ส่งต่อ ตรวจผล ส่งกลับแก้ไข และปิดเรื่อง
- จัดการผู้ใช้ หน่วยงาน และ Master Data
- ดู Dashboard, Report และ Audit Log
- ลบเรื่องร้องเรียนแบบ Soft Delete
- เปิดเผยตัวตนของเรื่อง Anonymous ได้เมื่อระบุเหตุผล โดยระบบบันทึก Audit Log
- เห็นข้อมูลส่วนบุคคลของผู้ร้องในเรื่องปกติ
- ส่งข้อความเพิ่มเติมถึงผู้ร้องทาง LINE จากเรื่องที่เข้าถึงได้ โดยต้องตรวจทานก่อนส่ง

### `admin` — ผู้ดูแลระบบ

- จัดการผู้ใช้ หน่วยงาน และ Master Data
- ดู Audit Log, Dashboard และ Report
- จัดการเรื่องร้องเรียนในฐานะเจ้าหน้าที่ศูนย์ได้ตาม implementation ปัจจุบัน
- สร้าง แก้ไข คัดกรอง ส่งต่อ ตรวจผล ส่งกลับแก้ไข และปิดเรื่องได้
- เห็นข้อมูลส่วนบุคคลของผู้ร้องในเรื่องปกติ
- ส่งข้อความเพิ่มเติมถึงผู้ร้องทาง LINE จากเรื่องที่เข้าถึงได้ โดยต้องตรวจทานก่อนส่ง
- ไม่สามารถเปิดเผยตัวตนของเรื่อง Anonymous หรือลบเรื่องร้องเรียน
- ตามข้อกำหนด Admin ต้องไม่สามารถจัดการบัญชี `super_admin`

### `officer` — เจ้าหน้าที่ศูนย์ดำรงธรรม

- ดูเรื่องร้องเรียนทั้งหมด
- สร้างและแก้ไขเรื่องร้องเรียน
- คัดกรอง จัดประเภท และกำหนดพื้นที่
- ส่งเรื่องไปยังหน่วยงานที่เกี่ยวข้อง
- ขอข้อมูลเพิ่มเติม ส่งแจ้งสถานะ และส่งข้อความที่กำหนดเองถึงผู้ร้องผ่าน LINE
- ตรวจสอบผลที่หน่วยงานส่งกลับ ส่งกลับไปแก้ไข หรือปิดเรื่อง
- เพิ่ม Timeline/Update และจัดการไฟล์แนบตามสิทธิ์
- ดู Dashboard, Report และ Export รายงาน
- เห็นข้อมูลส่วนบุคคลของผู้ร้องในเรื่องปกติ
- ไม่สามารถจัดการผู้ใช้ Master Data หน่วยงาน หรือ Audit Log

### `chief` — หัวหน้าเจ้าหน้าที่ศูนย์ดำรงธรรม

- เป็นหัวหน้าฝั่งศูนย์ดำรงธรรม
- ทำงานกับเรื่องร้องเรียนได้เหมือน `officer`
- ดู Dashboard, Report และ Export รายงาน
- เห็นข้อมูลส่วนบุคคลของผู้ร้องในเรื่องปกติ
- ไม่สามารถจัดการผู้ใช้ Master Data หน่วยงาน หรือ Audit Log
- **หมายเหตุ:** ใน implementation ปัจจุบัน สิทธิ์ทางเทคนิคของ `chief` และ `officer` เกือบเหมือนกัน ยังไม่มี Action อนุมัติเฉพาะหัวหน้าที่แยกชัดเจน

### `agency_officer` — เจ้าหน้าที่หน่วยงานปลายทาง

- เห็นเฉพาะเรื่องที่ถูกส่งให้หน่วยงานของตน
- รับเรื่อง ส่งคืนเรื่อง เริ่มดำเนินการ และส่งผลกลับ
- เพิ่มความคืบหน้า แนบไฟล์ ขอข้อมูลเพิ่มเติม และส่งข้อความทาง LINE ถึงผู้ร้องในเรื่องที่มีสิทธิ์
- ดู Dashboard เฉพาะข้อมูลของหน่วยงานตน
- ดูการแจ้งเตือนที่เกี่ยวข้องกับงานของตน
- ไม่เห็นข้อมูลส่วนบุคคลของผู้ร้อง
- ไม่สามารถส่งต่อหรือปิดเรื่องแทนศูนย์ดำรงธรรม
- หน้าเว็บไม่อนุญาตให้สร้างหรือแก้ไขข้อมูลหลักของเรื่อง แต่ API ปัจจุบันยังให้ Agency เรียก `POST/PUT /api/complaints` ได้ จึงเป็นจุดที่ควรปรับสิทธิ์ให้ตรงกัน

### `agency_head` — หัวหน้าหน่วยงานปลายทาง

- มีสิทธิ์ดำเนินการเรื่องของหน่วยงานเหมือน `agency_officer`
- ดู Dashboard สรุปของหน่วยงานตน
- Backend อนุญาตให้ Export Excel ได้
- จัดการกลุ่มแจ้งเตือน LINE ระดับหน่วยงานได้
- ไม่เห็นข้อมูลส่วนบุคคลของผู้ร้อง
- ไม่สามารถส่งต่อหรือปิดเรื่องแทนศูนย์ดำรงธรรม
- **หมายเหตุ:** Frontend ปัจจุบันยังไม่อนุญาตให้ `agency_head` เข้าหน้า Report แม้ Backend จะอนุญาต Export Excel

### `executive` — ผู้บริหาร

- ดู Dashboard ภาพรวม
- ดู Report และ Export รายงาน
- เป็นสิทธิ์แบบ Read-only
- ไม่สามารถเข้าหน้ารายการ/รายละเอียดเรื่องร้องเรียนใน implementation ปัจจุบัน
- ไม่สามารถสร้าง แก้ไข ส่งต่อ อัปเดต หรือปิดเรื่อง
- ไม่เห็นข้อมูลส่วนบุคคลของผู้ร้อง

### `public` — ประชาชนทั่วไปแบบ Guest

- ไม่ต้องมีบัญชีและไม่ต้อง Login
- ยื่นเรื่องผ่าน `/public/complaints/new`
- ติดตามสถานะด้วยเลขที่เรื่องผ่าน `/public/track`
- เห็นเฉพาะข้อมูลสถานะที่เปิดเผยต่อประชาชน
- ไม่สามารถเข้าถึงข้อมูลภายในหรือเรื่องของผู้อื่น

> `public` เป็น Role ที่มีอยู่ในตาราง `roles` เพื่อใช้อธิบายสิทธิ์เชิงระบบ แต่ไม่มีบัญชีในตาราง `users`

### Citizen — สมาชิกประชาชน

Citizen ไม่ใช่ Role ในตาราง `users` แต่เป็นผู้ใช้อีกระบบหนึ่งซึ่งเก็บในตาราง `citizens` และใช้ JWT/เส้นทาง API แยกจากเจ้าหน้าที่

- สมัครสมาชิกและ Login ด้วยอีเมล/รหัสผ่าน หรือ LINE Login
- ยื่นเรื่องและผูกเรื่องเข้ากับบัญชีของตน
- ดูรายการและรายละเอียดเรื่องของตนเอง
- แก้ไขข้อมูลส่วนตัวและเปลี่ยน/ตั้งรหัสผ่าน
- ตั้งค่าการแจ้งเตือนและเชื่อม/ยกเลิกการเชื่อม LINE
- เลือกปกปิดตัวตนตอนยื่นเรื่องได้
- ไม่สามารถดูเรื่องหรือข้อมูลของประชาชนคนอื่น
- Citizen JWT ไม่สามารถใช้เรียก Staff API ได้

## 3. การมองเห็นข้อมูลผู้ร้อง

| ประเภทผู้ใช้ | เรื่องปกติ | เรื่อง Anonymous |
|---|---|---|
| `super_admin` | เห็นข้อมูลผู้ร้อง | ถูกปกปิด แต่ขอเปิดเผยได้เมื่อระบุเหตุผล |
| `admin` | เห็นข้อมูลผู้ร้อง | ถูกปกปิด |
| `officer`, `chief` | เห็นข้อมูลผู้ร้อง | ถูกปกปิด |
| `agency_officer`, `agency_head` | ไม่เห็นข้อมูลส่วนบุคคล | ถูกปกปิด |
| `executive` | ไม่เห็นข้อมูลส่วนบุคคล | ถูกปกปิด |
| เจ้าของเรื่องที่เป็น Citizen | เห็นข้อมูลและเรื่องของตนเอง | เห็นเรื่องของตนเองตามปกติ |

## 5. เงื่อนไขการใช้บัญชี Seed

- รหัสผ่านในฐานข้อมูลเก็บเป็น bcrypt hash ไม่ได้เก็บเป็น Plaintext
- บัญชีข้างต้นจะถูกสร้างเมื่อ MySQL เริ่มต้นฐานข้อมูลใหม่จาก Seed
- ค่า `agency_id` อาจต่างกันในแต่ละฐานข้อมูล ระบบจึงอ้างอิงหน่วยงานศูนย์ด้วย `is_center` และอ้างอิงหน่วยงานปลายทางด้วยข้อมูลในตาราง `agencies`
- หากใช้ Docker volume/ฐานข้อมูลเดิมที่เคยแก้รหัสผ่านหรือข้อมูลผู้ใช้ บัญชีจริงอาจไม่ตรงกับรายการนี้
- ไม่ควรนำ Username/Password ชุดนี้ไปใช้ใน Production
- Production ต้องเปลี่ยนรหัสผ่าน Seed ทันที และสร้างบัญชีตามผู้ใช้งานจริง
