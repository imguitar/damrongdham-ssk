# เรื่องที่ถูกเร่งรัด และเรื่องเกินกำหนด SLA

เอกสารนี้อธิบายความหมายและความแตกต่างระหว่าง **เรื่องที่ถูกเร่งรัด (Escalation)** กับ **เรื่องเกินกำหนด SLA (Overdue)** ตามพฤติกรรมของระบบ Damrongdham SSK

> อัปเดตล่าสุด: 13 กันยายน 2569

## 1. สรุปความแตกต่าง

ทั้งสองรายการเป็นคนละเงื่อนไขและใช้ติดตามความเสี่ยงคนละด้าน

| หัวข้อ | เรื่องที่ถูกเร่งรัด | เรื่องเกินกำหนด SLA |
|---|---|---|
| ความหมาย | เรื่องที่ไม่มีการอัปเดตความคืบหน้าเป็นเวลานาน | เรื่องที่เลยวันครบกำหนดดำเนินการแล้ว |
| สิ่งที่ใช้วัด | จำนวนวันจากความคืบหน้าครั้งล่าสุด | วันที่ปัจจุบันเทียบกับ `due_date` |
| เกณฑ์ | L1 = 30 วัน, L2 = 45 วัน, L3 = 52 วัน | `วันปัจจุบัน > due_date` |
| จุดประสงค์ | กระตุ้นให้เจ้าหน้าที่หรือหน่วยงานอัปเดตและดำเนินการต่อ | แจ้งว่าเรื่องใช้เวลาเกินมาตรฐานของประเภทเรื่อง |
| ผลในระบบ | กำหนด `escalation_level` เป็น 1, 2 หรือ 3 | กำหนด `is_overdue = true` |
| ความสัมพันธ์ | อาจถูกเร่งรัดโดยที่ยังไม่เกิน SLA | อาจเกิน SLA โดยที่ยังไม่ถูกเร่งรัด |

## 2. เรื่องที่ถูกเร่งรัด (Escalation)

เรื่องที่ถูกเร่งรัด คือเรื่องที่ยังอยู่ระหว่างดำเนินการ แต่ไม่มีการบันทึกความคืบหน้าเป็นเวลานาน ระบบตรวจสอบทุกวันเวลา 08:00 น. ตามเขตเวลา Asia/Bangkok

### 2.1 ระดับการเร่งรัด

| ระดับ | เงื่อนไข | ความหมาย |
|---|---|---|
| L1 | ไม่มีความคืบหน้าอย่างน้อย 30 วัน | เริ่มแจ้งเตือนให้เร่งอัปเดต |
| L2 | ไม่มีความคืบหน้าอย่างน้อย 45 วัน | เรื่องยังคงค้าง จึงยกระดับการแจ้งเตือน |
| L3 | ไม่มีความคืบหน้าอย่างน้อย 52 วัน | เรื่องค้างเป็นเวลานาน ต้องเร่งดำเนินการโดยด่วน |

### 2.2 เรื่องที่อยู่ในขอบเขต

Implementation ปัจจุบันตรวจสอบเรื่องที่มีสถานะต่อไปนี้

- `ASSIGNED` — ส่งต่อหน่วยงานแล้ว
- `ACCEPTED` — หน่วยงานรับเรื่องแล้ว
- `IN_PROGRESS` — อยู่ระหว่างดำเนินการ

เรื่องที่ส่งผลแล้ว ปิดแล้ว หรือถูกปฏิเสธ จะไม่อยู่ในขอบเขตการเร่งรัด

### 2.3 การเริ่มนับและรีเซ็ต

- ถ้ามีการอัปเดตความคืบหน้า ระบบนับจาก `last_progress_at`
- เมื่อเพิ่มความคืบหน้าใหม่ ระบบควรตั้ง `last_progress_at = NOW()` และรีเซ็ต `escalation_level = 0` เพื่อเริ่มนับรอบใหม่
- หากยังไม่เคยมีการอัปเดต โค้ดปัจจุบันใช้ `created_at` เป็นวันที่เริ่มนับ

การถูกเร่งรัดไม่ได้หมายความว่าเรื่องเกิน SLA เสมอไป แต่หมายความว่าเรื่องไม่มีความเคลื่อนไหวนานถึงเกณฑ์ที่กำหนด

## 3. เรื่องเกินกำหนด SLA (Overdue)

SLA คือระยะเวลามาตรฐานที่กำหนดให้ดำเนินการเรื่องร้องเรียน โดยแต่ละประเภทเรื่องสามารถมีจำนวนวัน SLA แตกต่างกัน

### 3.1 การคำนวณวันครบกำหนด

ระบบคำนวณวันครบกำหนดเมื่อศูนย์ดำรงธรรมส่งต่อเรื่องให้หน่วยงาน

```text
due_date = วันที่ส่งต่อหน่วยงาน (assigned_at) + จำนวนวัน SLA ของประเภทเรื่อง
```

SLA ใน Phase ปัจจุบันนับรวมวันเสาร์ อาทิตย์ และวันหยุด

### 3.2 เงื่อนไขเกินกำหนด

เรื่องจะถูกระบุว่าเกินกำหนดเมื่อ

```text
วันปัจจุบัน > due_date
และสถานะไม่ใช่ CLOSED หรือ REJECTED
```

ระบบตรวจสอบทุกวันเวลา 08:00 น. และตั้งค่า `is_overdue = true` ให้เรื่องที่เพิ่งเกินกำหนด

`is_overdue` เป็น Flag ประกอบสถานะ ไม่ใช่สถานะ Workflow ใหม่ ดังนั้นเรื่องหนึ่งอาจมีสถานะเป็น `IN_PROGRESS` และมี `is_overdue = true` พร้อมกันได้

## 4. ตัวอย่างสถานการณ์

### ตัวอย่างที่ 1: ถูกเร่งรัด แต่ยังไม่เกิน SLA

- ประเภทเรื่องกำหนด SLA 60 วัน
- เรื่องยังเหลือเวลาอีก 30 วันก่อนครบกำหนด
- ไม่มีการอัปเดตความคืบหน้ามาแล้ว 30 วัน

ผลคือ **ถูกเร่งรัดระดับ L1 แต่ยังไม่เกิน SLA**

### ตัวอย่างที่ 2: เกิน SLA แต่ยังไม่ถูกเร่งรัด

- ประเภทเรื่องกำหนด SLA 7 วัน
- เรื่องเลย `due_date` มาแล้ว 2 วัน
- เจ้าหน้าที่เพิ่งอัปเดตความคืบหน้าเมื่อวาน

ผลคือ **เกิน SLA แต่ยังไม่ถูกเร่งรัด** เพราะยังไม่ถึง 30 วันนับจากความคืบหน้าล่าสุด

### ตัวอย่างที่ 3: ทั้งถูกเร่งรัดและเกิน SLA

- เรื่องเลย `due_date` แล้ว
- ไม่มีการอัปเดตความคืบหน้ามาอย่างน้อย 52 วัน

ผลคือ **เกิน SLA และถูกเร่งรัดระดับ L3 พร้อมกัน**

## 5. ความหมายเมื่อนำไปใช้ติดตามงาน

- รายการ **เรื่องที่ถูกเร่งรัด** ใช้ค้นหาเรื่องที่ไม่มีความเคลื่อนไหวและควรติดตามให้หน่วยงานอัปเดตผล
- รายการ **เรื่องเกินกำหนด SLA** ใช้ค้นหาเรื่องที่ดำเนินการเลยเวลามาตรฐานแล้ว แม้อาจมีการอัปเดตความคืบหน้าอย่างต่อเนื่องก็ตาม
- การแสดงทั้งสองข้อมูลแยกกันช่วยให้แยกได้ว่าเรื่องมีปัญหาเพราะ **ไม่มีการอัปเดต** หรือเพราะ **ใช้เวลาเกินกำหนด**

## 6. ข้อสังเกตจาก Implementation ปัจจุบัน

เอกสาร Planning ระบุว่า ถ้าเรื่องยังไม่เคยมีความคืบหน้า การเร่งรัดควรเริ่มนับจาก `accepted_at` หรือวันที่หน่วยงานรับเรื่อง แต่ Scheduled Job ปัจจุบันใช้ `created_at`

ผลที่อาจเกิดขึ้นคือ เรื่องที่ถูกสร้างไว้นานก่อนหน่วยงานรับเรื่อง อาจถูกเร่งรัดเร็วกว่าหลักการในเอกสาร Planning ควรพิจารณาปรับให้ใช้วันที่รับเรื่องหรือกำหนด Anchor ให้เป็นมาตรฐานเดียวกัน
